# gtnh-determinism 0.13.0

AE2 meteorites. They were absent from every corpus this repo has ever produced, and once made to
appear they turned out to be route-dependent. Both are fixed.

Nothing in the vanilla-dungeon or village-chest work changed since 0.12.0; the routemap bundle
regenerated against this build is byte-identical to the 0.12.0 one apart from the meteorites.

## Fixed

### AE2 meteorites never generated in a probed world

Not a collection gap — the meteorites were not there. `MeteoriteWorldGen.generate` never touches
`MeteoritePlacer` at all: it calls `TickHandler.addCallable(world, new MeteoriteSpawn(...))`, and
`MeteoriteSpawn` is an `IWorldCallable` whose `call(World)` does the placing on a later server
**tick**. A real client ticks continuously so meteorites appear; the probe generated chunks flat out
and shut the server down with the queue still full.

Measured before the fix, 25 seeds at warm radius 30: **zero `TileSkyChest`**, with
`World/AE2/spawndata` empty afterwards. An expectation is load-bearing here, because
`MeteoriteWorldGen` seeds one candidate per `minMeteoriteDistance` grid cell (707 blocks) and a
single radius-60 window therefore holds only a couple — zero in one window proves nothing. The
comparison that does carry is the post-fix corpus at the same settings: **32 meteorites over 25
seeds**, against zero before. Across 25 seeds it is decisive.

A correction to an earlier draft of this file, which said `meteoriteSpawnChance 0=0.3` gates whether
a meteorite exists and put the expectation at ~13.8 with p ~ 7e-08. It does not gate existence —
there is no `if (check == 1)` around the `addCallable`. Every grid cell queues a spawn; the roll only
chooses the **starting depth**, `spawnSurfaceMeteor ? 180 + rng.nextInt(20) : 128`. The true rate is
higher than that model gave, so the direction of the conclusion is unaffected, but the number was
built on a misreading and should not be quoted.

`probe.drainticks` (default on, `=false` to disable) runs AE2's own `TickHandler.processQueue` in a
bounded loop after the walk and before the snapshot. Measured: **14,924 callables drained in 61-72
passes**, and meteorites go from 0 to 5 at radius 60 on `-1636594104014467454`. It warns rather than
returning quietly if the queue does not empty.

**This is not AE2-specific.** Anything a mod defers to a callable queue was missing from every
corpus, statistic and map this repo has produced. AE2 is simply the case with the highest loot value
attached — meteorites carry the Calculation, Engineering, Logic and Silicon presses.

### Warm batches leaked meteorites between seeds

Exposed immediately by the above: with meteorites finally being placed, **28 of 43 distinct positions
appeared in more than one seed**, one of them in seven, identically under both walk orders. Different
seeds have different terrain, so a shared coordinate is contamination.

`teardownAllWorlds` already deletes the whole save folder including `World/AE2`, so disk state was
never the problem. The leak was in memory: a warm batch never restarts the server,
`WorldData.instance()` is a singleton created once at server start, its spawn data still listed every
earlier seed's meteorites, and `MeteoriteWorldGen$ExistingMeteoriteSpawn` re-places **known**
meteorites into newly generated chunks.

`probe.resetae2` (default on) cycles `onServerStopping()` / `onServerAboutToStart()` at the top of
`recreateWorlds`. Shared positions **28 -> 0**, and the per-arm count falls 43 -> 38 because one
seed's craters stop being rebuilt in the next.

### Meteorite existence was route-dependent

With the corpus finally trustworthy: 25 seeds, rows against spiral, **2 meteorites of 38 existed
under one walk order and not the other**, against a same-order floor of **0**. Drift was **0** — where
a meteorite existed in both, it sat at the identical block.

That split is the diagnosis. Every input is seed-pure except one:

| input | source | route-dependent |
|---|---|---|
| which grid cell, and the 0.3 roll | `Platform.seedFromGrid(rand, worldSeed, gridX, gridZ)` | no |
| starting `y` (`MeteoriteSpawn.depth`) | `Random.nextInt` on that stream, or literal 128 | no |
| is the ground landable | `getBlock` vs `validSpawn`/`invalidSpawn`, **live world, at tick time** | **yes** |

`Ae2MeteoriteSitingMixin` answers those reads from `TerrainOracle`. All three `getBlock` calls in
`spawnMeteoriteCenter` are covered (`require = 3`) because all three are siting tests taken before
anything is written — two against `validSpawn`, one against `invalidSpawn`. `tryMeteorite` re-enters
up to 20 times stepping `y` down by 15, about six samples from the default depth, all through those
same call sites. The crater carving afterwards still reads and writes live terrain.

The deferral to a tick is left alone deliberately: a crater spans many chunks and carving it during
populate would write into ungenerated neighbours. Timing was never the defect.

Result: **2 differences of 38 -> 0 of 44**, and `TileSkyChest` is the only container type whose count
moves, so the redirect touches meteorite siting and nothing else.

**Balance: +11.4% meteorites.** 50 seeds, paired:

| | seeds | stock | virgin | change |
|---|---:|---:|---:|---:|
| batch 1 (separate jar builds) | 25 | 38 | 44 | +15.8% |
| batch 2 (one jar, lever flipped) | 25 | 32 | 34 | +6.2% |
| **pooled** | **50** | **70** | **78** | **+11.4%** |

95% CI (paired bootstrap) **[+2.6%, +22.2%]**, paired permutation **p = 0.0385**. Per-seed: 10 up, 2
down, **38 tied** — the typical world is unchanged and the lift is population-level. Virgin terrain
has fewer unlandable surfaces because decoration puts trees, water and structure blocks where virgin
has grass or stone, so more candidate sites pass. An earlier **+15.8%** figure from 25 seeds was the
high end of the noise and should not be quoted; at that size the CI and the permutation test
disagreed (p = 0.071).

**Balance, second axis: meteorites land shallower.** This was missed in an earlier draft, which
claimed depths were unchanged. Over 25 seeds, taking only meteorites present at the same `(x,z)` in
both arms so that existence differences do not contaminate the comparison:

| virgin y - stock y | meteorites |
|---|---:|
| +0 | 14 |
| +15 | 16 |
| +30 | 1 |
| negative | **0** |

Strictly monotone: **17 of 31 rise, none sink**. The step size is exactly the 15 of `tryMeteorite`,
so the fix is not nudging meteorites — it is making the downward scan *stop one rung earlier*,
because virgin terrain answers `validSpawn` where the live world did not. Since the scan runs top
down, a read that stops rejecting can only move a meteorite up. The same effect explains the count
lift: sites that stock scanned past now accept.

Shallower means more of them break the surface, so the visible-crater rate goes up somewhat relative
to stock. Burial itself is untouched and remains stock behaviour — see below.

Revert with `-Dgtnhdet.meteorsiting=false`. The determinism goes with it — the live read *is* the
nondeterminism.

### Not a bug: most meteorites are buried

Worth writing down because it looks like a collection failure and is not. A meteorite whose centre
lands below the surface leaves no crater and no sky stone on a surface render, and on
`-1636594104014467454` two of the five (Meteorites 1 and 4, buried 14 and 17 blocks) have **zero**
sky-stone pixels at the surface.

That is stock AE2-GTNH, and the mechanism is arithmetic rather than chance. `MeteoriteSpawn` starts
at `spawnSurfaceMeteor ? 180 + rng.nextInt(20) : 128` and `tryMeteorite` steps `depth -= 15` until
the centre block is in `validSpawn`. The landing `y` is therefore congruent to the starting depth
mod 15, and the centre ends up `(surface - start) mod 15` blocks under the ground — a roughly
uniform 0-14, set by a residue nobody chose.

The prediction is checkable and checks out. `128 mod 15 = 8`, so the 70% of meteorites taking the
deep branch must land at `y = 8 (mod 15)`: measured **22 of 32 stock (69%)** and 25 of 34 virgin, and
the five on `-1636594104014467454` sit at y = 83, 58, 68, 68, 83, i.e. residues 8, 13, 8, 8, 8.

Depth alone does not explain the missing crater, though, and that is the part worth understanding.
`MeteoritePlacer`'s constructor counts how many blocks in a 30x26x30 box around the centre can see
the sky — note the box reaches only **+10 above** the centre (`y - 15 .. y + 10`) — and stores it as
`skyMode`. Placement is then gated:

| `skyMode` | effect |
|---|---|
| `> 10` | `placeCrater` |
| `> 3` | `decay`, the collapse and scatter pass |
| otherwise | meteorite body and chest placed, **no crater, no fallout** |

The threshold is 11 blocks out of 23,400, so it is really "does any part of the box reach open air".
A centre buried more than ~10 blocks has no sky-visible block in range, `skyMode` is 0, and the
meteorite is built entirely inside the rock with no surface expression whatsoever. Since burial is
uniform 0-14 from the lattice above, roughly a third of all meteorites are invisible from the surface
by construction. A second switch does the same job independently: if any block in the column
`y - 15 .. y - 2` is air, `solid` is false and `skyMode` is forced to 0, so a cave under the impact
point removes the crater at any depth.

Predicted against `-1636594104014467454`, crater iff `y + 10 >= surface`:

| | centre y | y+10 | surface | predicted | observed |
|---|---:|---:|---:|---|---|
| Meteorite 1 | 83 | 93 | 97 | no crater | no surface trace |
| Meteorite 2 | 58 | 68 | 63 | crater | crater |
| Meteorite 3 | 68 | 78 | 73 | crater | crater |
| Meteorite 4 | 68 | 78 | 85 | no crater | no surface trace |
| Meteorite 5 | 83 | 93 | 88 | crater | crater |

Five of five. Nothing here is a defect to fix — it is what the mod does — but any future "the
meteorite is missing" report should be checked against the surface height before being treated as
one.

### Meteorites on the map

`TileSkyChest` is an `ISidedInventory`, so chest inventories were collected the moment meteorites
existed. Added: a `meteorite` source label in `fullgen-loot-csv.py` (by container type — meteorites
never reach `ChestGenHooks`, so no `chesttrace` line will ever name one), meteorite POIs in
`build_world_bundle.py`, and a `meteorite` layer in `routemap/layers.js` marked chest-bearing so the
inventory shows in the popup. On `-1636594104014467454`: **5 meteorites, 5 POIs**, 1729 -> 1734 chests
with nothing else moved.

Sky stone also got a block palette entry, so craters render as the near-black `(27, 28, 28)` they
should be instead of falling through to the biome colour and coming out grass green. The trap to
remember: `worldrender.py` has **two** tables, and `build_lookup` reads `BLOCKS.get(name)` first and
`continue`s when it misses. A `BLOCK_META` entry on its own therefore renders nothing — the block
stays unknown and takes `col[unknown] = bcol * 0.92`. A block needs a default in `BLOCKS` before its
per-metadata table is ever consulted. Sky stone was added to `BLOCK_META` alone at first and rendered
bright green; the surrounding grey ring that made it look correct was `minecraft:stone` exposed by
the crater, never the meteorite.

## Known limits

Unchanged from 0.12.0 unless noted. Read these before describing anything here as "deterministic
worldgen".

- **Blocks are roughly 75% route-dependent** (72-79% of chunks over 25 seeds, same-order floor
  0.1-0.5%). Untouched. Meteorite siting is now insulated from it, but nothing else is.
- **Route-dependent lakes demolish finished structures** — 12 dungeon chests filled in both walk
  orders and then deleted by a BoP poison lake in one.
- **Thaumcraft greatwood tree chests**: 17 against 47 across walk orders, spiral >= rows on all 25
  seeds. A monotone bias, so not RNG skew and not fixable with a fork.
- **Minecart chests remain invisible**: 156 `EntityMinecartChest` at radius 60, ~930 stacks of
  `mineshaftCorridor`, about 23% of the vanilla-dungeon loot volume. `buildSearchReport` walks tile
  entities only, so routemap chest coverage is capped near 92%.
- **NEW — meteorite CRATERS are not covered by the siting fix, but measured clean.**
  `Ae2MeteoriteSitingMixin` redirects `spawnMeteoriteCenter` only. The two reads deciding whether a
  crater is carved live in `MeteoritePlacer`'s **constructor** and are still against the live world:
  `canBlockSeeTheSky` over the 30x26x30 `skyMode` box, and the `solid` scan of the column
  `y - 15 .. y - 2` that zeroes `skyMode` outright on finding air.

  Measured 2026-09-10, 25 seeds at warm r30 (15 of them with a meteorite in window), rows against
  spiral, via `scripts/diff-craters.py`: 25 meteorites per arm at identical `(x, y, z)`, **0 crater
  differences and 0 decay differences**. But `skyMode` itself **differs on 10 of 25** — e.g. 1661 vs
  1531, 762 vs 797 — so the input *is* route-dependent, it simply never moved far enough to cross a
  threshold. This is a margin result, not an immunity result. `skyMode` came out **0 for 5 and above
  10 for 20, never once in 1..10** across all 50 observations, so meteorites sit far from the cut and
  a wobble of ~100 changes nothing. A meteorite landing near `skyMode = 12` would be a different
  story; none did.

  A consequence worth noting: since no `skyMode` ever landed between the two thresholds, AE2's
  `> 3` (decay) and `> 10` (crater) are in practice the same test — "is there any sky at all".

  Do **not** try to measure this with a terrain diff. Blocks are ~75% route-dependent chunk-wise and
  a crater is a few thousand blocks against that background; the signal drowns. Diffing the single
  integer that makes the decision is what works.
- **NEW — other mod singletons are unaudited.** AE2's `WorldData` surviving the warm recreate was
  found only because meteorites are visible loot. Any mod holding server-lifetime state that the
  recreate does not reset can carry one seed's data into the next, and a mod leaking something the
  corpus does not record would stay invisible. The test that found it generalises: a position
  appearing at an identical coordinate in more than one seed of a warm batch is contamination.

## Also

- `scripts/diff-meteorites.py` (new): separates meteorite **existence** from **drift**, which a
  position-keyed diff conflates and double-counts. Refuses a verdict over zero seeds. Carries the
  caveat that the probe drains the callable queue at one fixed point, so a clean result shows
  stability under that discipline rather than in normal play.
- Diagnostics, all inert without their flags and gated on AE2 being installed: `-Dprobe.wgdump`
  (lists FML's registered `IWorldGenerator`s), `-Dprobe.meteortrace` (AE2's own
  `isWorldGenEnabled` verdict), `-Dgtnhdet.meteortrace` (`generate` call counts, the spawn-chance
  roll, and every `spawnMeteoriteCenter` verdict).
- AE2 added as a `compileOnly` dependency — Mixin's annotation processor resolves `targets=` at
  compile time, same reason the file already carries Et Futurum and TooMuchLoot.
