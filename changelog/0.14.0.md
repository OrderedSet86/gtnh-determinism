# gtnh-determinism 0.14.0

Since `970e4eafdf3c5103d1b360286ea072f4e13f2eba` (0.13.0).

## Summary

- **Two startup crashes are fixed.** 0.13.0 crashes on GTNH 2.9.0-RC-1, RC-2 and current daily builds
  (caused by Mobs-Info 0.6.0), and on 2.9.0-beta-1 (caused by GregTech version detection).
- **Mineshaft minecart chests are pinned and on the route map.** Whether each chest exists now comes from
  the seed and the chest's position. In 25 test seeds this removes 18 of 19 generation-order differences.
  The pin is on by default.
- **This release changes worldgen.** The mineshaft pin moves some underground blocks, so a world or seed
  list made with 0.13.0 does not carry over.
- **GregTech ore veins on 2.9.0-beta-1** do not depend on the order chunks generate in, the same as on
  2.9.0-beta-3.
- **Horse spawns on RC-1 and later.** Two of the seven horse draws had escaped the fix there. Both are
  pinned again.
- **The route-map generator ships with each release** as `GTNH-Routemap-windows.zip` and
  `GTNH-Routemap-unix.zip`.
- **Seed-search tooling:** stage-0 gates for the hammer% rush and an AE2 meteorite crater prefilter.
- **Tested on** 2.7.4, 2.8.4, 2.9.0-beta-3, 2.9.0-RC-1, RC-2 and the 2026-10-11 daily.
- **Known limits:** 1 mineshaft chest in 25 test seeds still depends on generation order. Mars meteorites
  are untested. GregTech 5.09.53.11 to 5.09.54.01 has code but no measurement.

The sections below have the detail and the measurements.

## What changes in a world

The mineshaft chest pin moves blocks unrelated to ore. On 2.9.0-beta-3, 154 of 2,401 chunks differ from
0.13.0 with the pin on and 17 with `-Dgtnhdet.mineshaftpin=false`, against a same-jar launch-to-launch
floor of 22. The differences sit at y 0 to 31, where mineshafts generate. The GregTech changes leave
output unchanged on GT 5.09.54.02 and later: their 17 of 2,401 is below that floor, and every class that
runs on that band is bytecode-identical apart from constant-pool index shifts from an added `allow = 2`.

The reference-seed route map (`-1636594104014467454`, 2.9.0-beta-3, overworld at radius 120) was rebuilt
with this build. Against the previous bundle, 5,137 of 5,142 containers are identical and 1,129 mineshaft
minecart chests are new to the map. The other 7 differences are 2 vanilla-dungeon chests that 0.13.0 generated
and this build does not, a new Witchery dispenser, a new escritoire, and 3 containers with different contents. All 7 are
6 to 30 blocks from a minecart chest, and each reproduces the previous bundle with
`-Dgtnhdet.mineshaftpin=false`, so they come from the pin's block movement. On the rebuilt run, 2,394 of
2,394 chests the prefilter predicts are present.

## Fixed

### Crash on 2.9.0-RC-1, and two horse-spawn draws that stopped being seed-stable

`gtnhdeterminism` 0.13.0 crashes at init on GTNH 2.9.0-RC-1, on the client and on a dedicated server:
`Critical injection failure: Redirector gtnhdet$forkedChestZ ... in worldgen.WorldGenDungeonsScanMixin`.
Nothing the jar hooks into changed. Mobs-Info 0.6.0, new in RC-1, registers a class transformer that runs
on every class using `java.util.Random`. Where `rand.nextInt(n)` is compared with a constant straight away,
the transformer replaces the call with `RandomComparison.nextInt(rand, n, constant, op)`. For an
ordinary `Random` that returns the same number, so the pack generates the same world. The call is no
longer a `Random.nextInt` call, though, so every mixin that picks a draw by position ("the 4th `nextInt`
in this method") counts wrong:

| mixin | on RC-1 with 0.13.0 |
| --- | --- |
| vanilla dungeon chest position | crash: chest Z (ordinal 4) has no target, and chest X's selector lands on chest Z |
| mineshaft corridor chests (new in this release) | crash: chest slot A (ordinal 1) has no target |
| mesa corridor chests (new, opt-in) | crash when opted in |
| horse spawn type, variant and health | **no error**: 2 of the 7 draws stayed on the clock-seeded entity RNG |

Mobs-Info's transformer keeps running, because Mobs-Info uses it to compute drop odds for NEI. The jar now
finds its draws in both call shapes:

- A new injection point, `RandomDrawPoint`, counts plain and rewritten `nextInt` calls as one sequence, so
  a draw is selected by its stock position on every pack.
- A draw that is never a comparison in stock code keeps one injector with `require = 1`.
- A draw that is a comparison gets a `@Redirect` for the plain shape and a `@WrapOperation` for the
  rewritten shape, in one `@Group` that requires the stock number of draws to bind. Otherwise the game
  refuses to start.
- The wrap takes the stock draw through Mobs-Info's call, so the random stream advances as it does
  without this jar.
- The Eldritch ring spawner roll is pinned by position with `require = 1`. It was not broken, but it
  matched every `nextInt` in the method, so nothing would have caught a future shift.

Verified by booting 2.7.4, 2.8.4, 2.9.0-beta-3 and RC-1 and disassembling the woven classes. On the first
three, every draw goes to the same plain redirect as in 0.13.0. On RC-1 the rewritten draws go to the
wraps and the rest to the redirects, at the same stock positions. A jar built with a wrong group count
refuses to start (`expected 8 invocation(s) but only 7 succeeded`).

Measured on RC-1, seed `-1636594104014467454`, radius 24: with Mobs-Info's rewrite on and off, ore veins,
all 227 containers (27 of them mineshaft minecarts) and all 9 horses are identical, and the chunk
difference (11 of 2,401) is at the launch-noise floor (12 of 2,401). Rows vs spiral gives the same
residuals as beta-3 with the same jar. 2.9.0-RC-2 and the 2026-10-11 daily build (GT 5.09.54.221), where a
player reported this crash, give the same result. See results/2026-09-25-2.9.0-RC-1-compatibility, Parts 4
and 5.

### GregTech version detection: crash on 2.9.0-beta-1, and a silent hole either side of it

Reported from a 2.9.0-beta-1 client (GT 5.09.52.594): `gtnhdeterminism` 0.13.0 stops the game at
`FMLInitializationEvent` with `InvalidInjectionException: @Redirect ... gtnhdet$virginStoneType could not
find any targets matching executeWorldgenChunkified(...WorldgenGTOreLayer$VeinPlacement;ZZ)I`.

GregTech rewrote its ore worldgen twice, so there are three shapes:

| Shape | GT band | Reroll probe | `executeWorldgenChunkified` |
|---|---|---|---|
| A | 5.09.50.119 to 5.09.52.30 (2.7.4, 2.8.4) | `Block.isReplaceableOreGen` ×10 | one declaration, selection writes |
| B | 5.09.52.31 to 5.09.54.01 (**2.9.0-beta-1**) | `StoneType.findStoneType` ×2 | one declaration, accept test fused with the write |
| C | 5.09.54.02 and later (2.9.0-beta-3) | `StoneType.findStoneType` ×2 | split into resolve, test and place |

`LateMixinLoader.gtOreMixin()` knew two shapes and told them apart with
`hasClass("gregtech.api.enums.StoneType")`. That class exists from 5.09.52.31, not 5.09.54.x, so every
shape-B pack got shape C's mixin, whose method descriptor matches nothing there. Six F4d injectors would
have failed right behind it, because their gate keyed on `hasClass("gregtech.common.ores.OreManager")`, a
class that also dates from 5.09.52.31. F4 is the vein reroll probe reading untouched terrain. F4d pins the
vein-identity decision to the vein's oreseed chunk.

The fixes:

- The new `GtOreShape` probes each target's bytecode: `resolveVeinPlacement` for C, `findStoneType` for B,
  `isReplaceableOreGen` for A, most specific first. F4d is gated on `GTWorldgenerator$WorldGenContainer`
  naming `resolveVeinPlacement` and `OreManager` naming `canSetOreForWorldGenOrAlreadySet`, the classes
  those mixins bind to.
- There is no version comparison. The rewrite came off a `-pre` branch, so the shapes interleave by tag
  number: `5.09.52.25-pre` is shape B, while the higher-numbered `5.09.52.26` and `5.09.52.30` are shape A.
- An unrecognised GregTech gets no ore mixin and a warning that names the jar.
- The new `WorldgenGTOreLayerFindStoneTypeMixin` restores F4 on shape B with a bare method selector (that
  whole band has one declaration) at `require = 2, allow = 2`.
- `WorldgenGTOreLayerMixin` (shape A) went from `require = 0` to `require = 10`, the probe call-site count
  on all 622 shape-A tags. At 0 it bound nothing, with no error, when it was the wrong choice.
- `WorldgenGTOreLayerMixin` now has the `GtOrePin.appliesTo` gate: the dimension whitelist and the
  `gtnhdet.orepin` off switch. Without it, a stock A/B arm on 2.7.4 and 2.8.4 could not be built.

### F4d backported to GT 5.09.52.31 to 5.09.54.01

F4 alone does not make shape B's vein choice seed-stable. `generateVein` passes the triggering chunk as
`chunkX/chunkZ`, and three things depend on it: the clipping window `[chunkX+2, chunkX+2+16)`, the probe
column `(chunkX+7, chunkZ+9)`, and `localDensity`. F4 makes only the read in the second one use untouched
terrain. The coordinates still move with the route, so vein identity still depends on it.

On shape C, four `@ModifyArg`s are enough, because GregTech already splits geometry, accept test and
placement, and stores a `generationSeed()` to rewind the RNG. Shape B has one fused call that also writes
the ore, and pinning its coordinates directly would move ore up to three chunks away, into chunks Forge
never asked for. So the split is rebuilt:

- `GTWorldGenContainerDryRunMixin` puts one `@Redirect` on the selection-loop call (`@At(ordinal = 1)`.
  Ordinal 0 is the cached path, which is the real per-chunk write). It calls once pinned to the oreseed
  inside a `GtOreDryRun` scope. If that verdict accepts the vein, it rewinds the RNG and calls again
  unpinned to place the ore. It returns the pinned verdict, so GregTech caches the oreseed-pure choice.
- `OreManagerDryRunSuppressMixin` suppresses the one `World.setBlock` in `setOreForWorldGen` during the dry
  run. `generateLayer` evaluates every `rng.nextInt` before that call, so suppressing it leaves the stream
  unchanged.
- `OreManagerVirginStoneB1Mixin` and `OreManagerVirginStoneB2Mixin` make the host-stone read that the test
  still makes use untouched terrain. There are two classes because `setOreForWorldGen` changed at
  5.09.53.11: `findStoneType(Block,int)` became `findStoneType(World,…)` and the `canGenerateInWorld` gate
  moved inside it. As separate classes, whichever one is offered must bind.
- The rewind uses `XSTR.getSeed`/`setSeed`, a plain read and a plain assignment with no scrambling, so it
  round-trips. It stands in for shape C's `placement.generationSeed()`.
- `GtOreFusedWorldgen` calls the fused overload by reflection. The build pins GT 5.09.54.115, where that
  signature does not exist in `WorldgenGTOreLayer` or its `GTWorldgen` superclass, so no compile-time
  type names it. It resolves the method from the vein instance and never through `Class.forName`, which
  would define the class before its mixins apply.

`VirginStoneType` has a new `atUngated` for the same 5.09.53.11 split. Below that version, stock's
`findStoneType` has no `canGenerateInWorld` gate, so the gated `at()` would add a dimension filter that
stock does not have. That case is reachable. `SethClay` claims `hardened_clay` but is restricted to
`DimNames.SETH`, so an Overworld mesa column is a hit in stock and a miss under `at()`. One flipped sample
of nine flips the reroll and selects a different vein. The orepin audit and `ASSERT_PROBE` cannot see it,
because it is a divergence from stock and not a route dependence.

Support by shape: A has F4 only (no dry run exists and none can be built), B has F4 and the backported
F4d, C has F4 and native F4d. `GtOrePin.logState()` prints which one applies, so each measurement run's log
records it.

**Measured** (results/2026-09-17-gt-shape-probe-beta1): real 2.9.0-beta-1 pack, seed
`-1636594104014467454`, radius 24, rows vs spiral, one jar with `gtnhdet.orepin` as the only lever.

- Vein-identity residual: 35 of 423 regions (8.27%) → 0. The control matches the 7.95% measured for shape
  C's Overworld, so this is the same defect and `orepin=false` is the stock arm.
- Shape C regression on 2.9.0-beta-3 (GT 5.09.54.133), same jar and lever: 38 of 423 (8.98%) mix and 1
  geometry → 0, 0 and 0. The new F4d gate and `allow = 2` leave the native path unchanged.
- `diff-veincache.py` exits 1 on the beta-1 full box for `only in one: 2`. Both regions decode to oreseed
  chunks (-29, -5) and (-35, 10), outside the radius-24 walk. Restricted to the walked box,
  `only_in_one` is 0 at every radius, while the control's signal survives every restriction.
- `geometry differs` has no meaning on shape B, which caches the layer and not a `CachedOreVein`, so there
  is no `placement` to compare.
- Whole-chunk hashes still differ in 67.6% of chunks (stock: 71.0%), because the pack has other open
  defects. That number is not a vein result.

On shape B, `VeinGenerateEvent` now reports the pinned verdict, not the triggering chunk's. That verdict
is the one GregTech caches, but listeners such as VisualProspecting see the change.

## Added

### Mineshaft corridor loot is visible, predictable and pinned

0.13.0 listed minecart chests as invisible: at radius 60 there were 156 `EntityMinecartChest`s with about
930 stacks, about 23% of the vanilla-dungeon loot volume, and route-map chest coverage stopped near 92%.
Corpora made before this build do not contain them.

- **Probe report** (`WorldgenProbe.buildSearchReport`): walks each chunk's entity list for
  `EntityMinecartChest` and writes those into the per-chunk `chests` array through the same
  `dumpInventory` serializer, with the position floored. `scripts/diff-chests.py --type=EntityMinecartChest`
  limits a diff to them.
- **Prefilter** (`MineshaftPrefilter`, `-Dprobe.prefilter.mineshaft=R` and
  `-Dprobe.prefilter.mineshaftloot=true`):
  - trigger cells come from an arithmetic copy of the `MapGenBase`/`MapGenStructure` protocol, warm-up
    `nextInt()` included. A golden check compares it with a dispatch pass once per process, and the
    prefilter falls back to dispatch only when the check fails or the generator overrides the formula
  - real starts are dispatched before chunk generation under the `villageStarts` reset rules
  - loot comes from replaying the real `StructureStart.generateStructure` per populate window against the
    `SeedProbeWorld` overlay, windows in ascending (cx, cz) order, with each `Random` reseeded by RWG's
    populate formula. `SeedProbeWorld.spawnEntityInWorld` now captures entities during an overlay.
  - contents and roll count are exact under F10, the box-relative chest refill fork in `ChestFillContext`,
    which already covered entities. The simulation leaves out `PopulateChunkEvent.Pre` draws, which matters only for
    chests the existence pin does not cover.
- **Fix jar** (`MineshaftCorridorChestMixin`): the two per-section `nextInt(100)` chest-existence draws in
  `Corridor.addComponentParts` come from a splitmix fork of (world seed, piece box anchor, draw index). The
  fork is keyed per piece anchor in a ThreadLocal and reset at HEAD. The stock draws are still consumed.
  The terrain checks `isLiquidInStructureBoundingBox` and the chest cell's air check are not pinned.
  `-Dgtnhdet.mineshaftpin=false` restores stock.

**Measured** (results/2026-09-17-mineshaft-multiseed): 25 seeds, radius 24, rows vs spiral, 2.9.0-beta-3,
one jar with `gtnhdet.mineshaftpin` as the only lever.

- Existence differences: 19 (in 13 of 25 seeds) → 1 (1 of 25). Contents and NBT differ in 0 chests in both
  arms.
- The 1 remaining difference is seed `-987654321012345678` at (-555, 27, -494). A block dump of the chunk
  shows `minecraft:stone` at the chest cell in the rows walk and `minecraft:rail` in spiral, so the
  corridor component exists in only one walk. That is a terrain verdict, not the draw this pins. Mineshaft
  loot is not route-independent yet.
- On 2.8.4 (results/2026-09-13-hammer-prefilter-validation, warm, radius 30, pin on in both arms), 4 of 564
  minecart chests differ in existence between walks. That run has no pin-off arm, so it gives the residual
  only.
- The hammer% steel gate has no measured in-game run yet. Do not trust it in game.

The pack registers Et Futurum's `MapGenMesaMineshaft`, which keeps the vanilla trigger formula (it
overrides only `getStructureStart`, checked in the 2.6.2.25-GTNH bytecode). Mesa-biome cells build
`MesaCorridor` pieces, which the default pin does not cover (`-Dgtnhdet.mesapin=true` turns on
`MesaCorridorChestMixin`). The mesa biome test can also resolve differently in the prefilter and in game
on a biome border. Mesa mineshafts are not predicted. They are rare near spawn on this pack, and F10 still
makes their contents position-pure.

### Route-map generator ships with the release

Each release has `GTNH-Routemap-windows.zip` and `GTNH-Routemap-unix.zip`. A player unzips one, runs it,
picks a Prism instance, types a seed, and gets an interactive map of that world's loot, points of
interest and ore veins in a browser. The generator turns the instance into a headless server, generates
the world with this release's fix and probe jars, and builds the map with gtnh-seedlib's builder. Java
comes from Prism's bundled runtime. The Windows zip needs nothing installed: it ships python.org's
embeddable CPython 3.12 with the numpy, pillow and certifi wheels. On macOS and Linux it runs the system
`python3`, which needs `pip install numpy pillow`. If the instance already has a `gtnhdeterminism` jar,
the generator uses that jar, so the map matches the world the player plays.

### Hammer% gates in the prefilter

- Worldless pre-gates at the top of `evaluate()`: `gate.mineshafttrig` and `gate.roguetrig`, centred on the
  origin, pure arithmetic.
- `gate.steel=N[,DIST]`: predicted village-chest steel (`VillageChestPrefilter.Predicted` now has
  `LootCounts` category counts) plus simulated corridor minecart steel within DIST of spawn. Kill rows
  have `blacksmith_steel`, `mineshaft_steel` and `steel_total` for tuning the bar. The loot simulation
  filters starts by DIST, which takes the stage from 2.6 s/seed to about 170 ms/seed (8-seed smoke test).
- `gate.toolloot=alumite=A,plate=P,hammer=H,rod=R[,dist=D]`: the TOOLS-chest total over all in-range
  Roguelike dungeons, with no early exit because the criteria sum across dungeons. It reads a new
  `Result.toolChests` on `RoguelikePrefilter`. Matching uses server display names. The material GTNH shows
  as Obzinite is `Alumite` on the server, so every string here uses Alumite.
- `seedsearch/hammer-hunt.py`: recounts from the raw row fields and prints any disagreement with the Java
  counters, with movable bars, kill-row histograms and output ready for `/tp`.
- The scripts forward the new settings: `PREFILTER_MINESHAFT`, `PREFILTER_MINESHAFTLOOT`,
  `PREFILTER_GATE_MINESHAFTTRIG/ROGUETRIG/STEEL/TOOLLOOT`, and `PREFILTER_GATE_PIECES`, which
  `prefilter-sweep.sh` never forwarded before.

Validated in results/2026-09-13-hammer-prefilter-validation (2.8.4, 25 seeds):

- Route stability, rows vs spiral, pin on: 564 and 562 minecarts, 4 existence differences (0.7%), 0
  contents, 0 NBT. The whole-world route background on the same seeds is 131 or more existence
  differences, all from known non-mineshaft causes. The 4 are the un-pinned liquid and air checks.
- Prediction vs full generation: 652 predicted, 643 present, contents 531 of 531 identical where
  predicted, 0 miscategorised. All 9 absent are minecarts. 12 of the 16 chests missed in the reverse
  direction belong to starts beyond the 45-chunk origin scan. Sweep with `PREFILTER_MINESHAFT=55`.
- The 2.8.4 blacksmith is vanilla `StructureVillagePieces$House2`, not Village Names' `*Weaponsmith*`. The
  chest-site table, measured on daily-707, never matched it, so blacksmith steel read 0. Four caller-local
  rows (5,1,5, category `villageBlacksmith`) fix that: 15 predicted, 15 present, 15 with identical contents.
- Calibration, 2,000 seeds, gates off: `steel_total>=4` within 320 blocks of spawn is 3 of 2,000,
  `alumite>=2` is 10 of 2,000, and all four loot bars together are 8 of 2,000. With the smeltery gate
  (about 12.5%), that is about 1 survivor per 1.3M seeds at 148 ms/seed gated. Kill rows have every count,
  so the bars can be tuned afterwards.

### Hodgepodge FAST_RANDOM changes every MapGenBase reseed stream

Hodgepodge's `fastRandom` speedup (`SpeedupsConfig.fastRandom` → `fastload.rand.MixinMapGenBase`) swaps
`MapGenBase.rand` for `StdLCG`. `StdLCG` uses the same LCG constants as `java.util.Random`, but its
`setSeed` stores the seed without the `^ 0x5DEECE66D` scramble, so every per-cell reseed in the vanilla
structure-trigger protocol starts from a different state. An offline `StdLCG` model reproduces the
dispatched lattice (5 of 5). The mineshaft trigger replica's golden check failed on seed
6638590251101633602: the replica predicted 8 cells, and the game dispatched 0 starts at them.

The replica now reads the live `rand` field's class: `StdLCG` → raw seed, `java.util.Random` → scrambled
seed, anything else → dispatch only. The golden check stays as the end-to-end guard. Villages,
strongholds, caves and the Roguelike, Witchery and oil modules dispatch the real, mixin-transformed code,
so this does not affect them. A new replica of a `MapGenBase` stream must check the `rand` field's class
first.

### AE2 meteorite prefilter and the biggest-crater hunt

`MeteorPrefilter` (`-Dprobe.prefilter.meteor=C` grid cells around the origin cell) replays each cell's
RNG through the real `Platform.seedFromGrid`: position, start depth, placer seed, size and lava. It replays
`tryMeteorite`'s descent against the placer's real `validSpawn`/`invalidSpawn` sets on untouched
`world.getBlock`, the same reads `Ae2MeteoriteSitingMixin` gives the game, and scores the carved volume by
integrating the crater paraboloid over the untouched heightmap. Gates: `gate.meteorsize` (candidate
filter, default 7.8), `gate.meteorrelief` (default 20) and `gate.meteorvol` (seed kill, kill rows list the
candidates). `seedsearch/meteor-hunt.py` ranks the results. Speed is 48 ms/seed at C=2 with default gates.

Measured on 2.9.0-beta-3 (AE2 rv3-beta-1050), identical on 2.8.4 (rv3-beta-695): golden seed existence 6
of 6, landing 5 of 5, size exact. Multiseed, 23 seeds, warm, radius 30: existence 14 of 14, landing 10 of
10, 0 false craters. The crater verdict is the one approximation left. `skyMode` reads live terrain, so
when population lowers a surface (lakes), a meteorite the untouched-terrain model calls buried makes a
crater. That happened 3 times in 10 in the multiseed window, all in that direction. No false positive has
been seen.

The staged funnel had two biases that hid a whole class of sites: the staged relief peek reached about
70 blocks where the disc needs 96, and the crater gate tested the centre column where `skyMode` reads a
±15 box. Both are fixed. `MeteorPrefilter.site` now scales its staging cuts with `gate.meteorrelief`, and
the burial reject is slope-aware against the lowest surface in the box. A game-free stage 0
(`seedsearch/rwg-analytic`, an exact port of RWG's `getNewNoise` blended height, checked to 1 block on 7
sites) ranks seeds by volume. Its best in a 1M-seed preview is **542,961 carved blocks** on seed
5550213969531321496 at (-376, 186). See results/2026-09-13-meteor-crater-hunt.

Notes for warm batches: `warm-probe.sh` does not create the out-template directory, and every seed fails
with `FileNotFoundException` when it is missing. A warm 25-seed batch at the default 6G heap ran out of
memory after 23 seeds. Radius 60 needs about 16G. Set `PROBE_XMX`.

## Known limits

- **The meteorite work covers the Overworld only, and meteorites also generate on Mars.** AE2 limits
  meteorites to an explicit dimension whitelist, unlike its other worldgen types: `isWorldGenEnabled`
  ends with `return !(!isGoodDimension && type == WorldGenType.Meteorites)`. This pack whitelists dim 0
  and dim 29 (Mars). The Nether and the End are disabled for every type, and the Twilight Forest is not on
  the list. Mars has no entry in `minMeteoriteDistance` or `meteoriteSpawnChance`, so it uses the `0=`
  entries: the same 707 grid and 0.3 roll, with Mars debris blocks.

  `Ae2MeteoriteSitingMixin` has no dimension guard, so it redirects on Mars too. `TerrainOracle` reads
  `theChunkProviderServer.currentChunkProvider` and goes through `OracleRngGuard.provideChunkIsolated`, so
  nothing in it is Overworld-specific, but it has never run against Galacticraft's chunk provider, and no
  probe has covered dim 29. Every meteorite figure (0 of 44 existence, 0 of 25 crater, +11.4%) is from dim
  0. Untested.
- **GregTech 5.09.53.11 to 5.09.54.01 has code but no measurement.** `OreManagerVirginStoneB2Mixin` is
  written and gated for that sub-band, but GTNH ships no pack in it. The measured band is 5.09.52.31 to
  5.09.53.10 (2.9.0-beta-1).
- **1 mineshaft chest in 25 test seeds still depends on generation order.** See Mineshaft corridor loot
  above.

## Open

- tools_agg category counting has not been checked against a full-generation Roguelike dump. The chests
  themselves are byte-identical. Only the counting is new.
- Seed-search winners still need in-world checks. On 2.9.0-beta-3, re-run survivors on a beta-3
  prefilter template first, because theme resolution at biome borders moves TOOLS loot.
- `-Dgtnhdet.mineshafttrace=true` changes worldgen: its full-piece live scan loads neighbouring chunks out
  of order (measured: a village workshop at x 984, z -586 moves from y 85 to 86). The 2026-09-17 trace run
  that ruled out `isLiquidInStructureBoundingBox` for the remaining mineshaft difference ran with that
  flag, so it needs a re-run once the scan stops loading chunks. `make-routemap.py` does not set the flag.
