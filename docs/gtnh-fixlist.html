The determinism jar: every fix, and why it was needed

What gtnhdeterminism-0.1.jar changes so that one seed always makes one world. Drop it into mods/ of a stock GTNH 2.7.4 instance — nothing else to install or configure. Companion to the full audit.

Why worldgen wasn't reproducible

Nearly every bug below is one of four patterns: randomness seeded from the clock instead of the world seed; a conditional branch that consumes random draws only sometimes, shifting everything rolled after it; decisions that read world state that may not exist yet, so the outcome depends on which direction you explored from; and registries stored in hash-ordered collections whose iteration order reshuffles every game launch.

The fixes

Village layouts scrambled every game launch

Forge/FML · affects every village

Symptom
Same seed, same village location — but different buildings each launch. The Tinkers smeltery or blacksmith might exist one session and be gone the next; chest loot "cycled between forms."
Cause
Forge stores the modded village-building handlers (Witchery, VillageNames, Tinkers, Railcraft, Forestry, WitchingGadgets…) in a HashMap keyed by class. Java hashes classes by memory address, so the iteration order — which sets both the RNG draw order and the building-list order — reshuffles on every JVM start.
Fix
After all mods register, the handler map is replaced with one sorted by class name. One canonical village per seed, for everyone.

Witchery structures: wrong dice, and a type roulette

Witchery · covens, wicker men, shacks, goblin huts

Symptom
Structures moved between runs (pre-fix); after the first fix they stayed put but the type still changed with your walking route — hay man one run, witch house or circle the next. Spawner contents also varied.
Cause
Three stacked bugs: worldgen rolled off world.rand (seeded from the clock at world load); the structure for each site was picked by shuffling one shared list in place every chunk, so the winner depended on how many chunks you generated on the way there; and the wicker man's spawner mob type was a separate world.rand roll.
Fix
All rolls use the seeded per-chunk RNG; the site's structure is chosen by shuffling a fresh, name-sorted copy of the list — a pure function of seed and location; the spawner type comes from the seeded roll too.

Thaumcraft: everything downstream of a terrain check

Thaumcraft 4 · nodes, totems, barrows, eldritch rings

Symptom
Node types/positions, totems, and barrows differed even within one session; barrow urn/crate loot never repeated.
Cause
All surface features shared one RNG stream, with extra draws gated on live terrain reads at chunk borders — one flipped check shifted every later roll. Barrow loot used world.rand; bonus nodes went to whichever chunk generated first; ring mazes were built on a background thread racing worldgen.
Fix
Every feature gets its own RNG derived from seed + chunk + feature; bonus nodes belong to the chunk that contains the feature; maze generation is synchronous and seeded; barrow loot rolls from the generation RNG.

GregTech ore veins occasionally rerolled

GregTech · ore vein identity and height

Symptom
Rarely, a known vein came up as a different ore (copper↔iron) depending on the direction you approached from — and one flip could cascade into neighboring veins.
Cause
Vein placement probed a column of live world blocks; if it hit air (cave, ravine, mountainside), the vein rerolled to the next type — and the result was cached for the whole region by whichever chunk generated first.
Fix
The probe accepts unconditionally: vein identity and height are pure functions of the seed.

RWG trees and decorations

Realistic World Gen · overworld decoration

Symptom
Trees (large pines, big trees) differed between runs; the noise also nudged other features sharing the decoration RNG.
Cause
Decorations bailed out early on terrain checks before consuming their rolls, shifting every later decoration's stream; big trees sized themselves with Math.random().
Fix
Every decoration takes exactly one draw from the shared stream and forks its own RNG from it; the clock-random tree sizing is pinned.

Tinkers slime islands: a one-word bug

TinkersConstruct · sky slime islands

Symptom
Slime islands existed at the same places but changed size, altitude, and shape every launch.
Cause
The generator receives the seeded RNG as parameter rand — but the code body used random, an instance field initialized as new Random() (clock-seeded). A classic variable-shadowing bug.
Fix
Use the seeded parameter throughout.

BiomesO'Plenty flora — and the dirt patches it dragged along

BiomesO'Plenty · grass/flower selection, underground dirt/gravel patches

Symptom
The last big launch-to-launch source: flora types swapped, and whole dirt/gravel patches relocated underground.
Cause
Each weighted grass/flower pick rolled with Math.random() and then walked a HashMap in memory-address order. Worse, the chosen generator consumed a different number of draws from the shared decoration RNG — relocating vanilla dirt/gravel patches downstream.
Fix
Flora tables keep registration order; the pick rolls from the seeded decoration RNG.

ProjectRed lily colors

ProjectRed · water lily dye yield

Symptom
Lilies grew in the same spots, but their color — i.e. which dye they yield — changed every launch. Dyes are run-relevant.
Cause
The flower color is rolled when the tile is created, using a clock-seeded default RNG.
Fix
Color derived from world seed + position: same lily, same dye, always.

Forestry village bees

Forestry · village bee house

Symptom
The village bee house building was stable, but the bee species inside, the apiary frames, and the flower garden varied per launch.
Cause
The building placed from the seeded structure RNG, but the contents rolled off world.rand.
Fix
Contents roll from a fork of the structure RNG — village bees are a property of the seed.

AE2 meteors already fixed upstream, 2022

Applied Energistics 2 · context

Cause
Meteor decisions were computed from per-chunk randomness for a cell-level choice — whichever chunk generated first won — with no persisted per-meteor seed.
Fix
eigenraven's grid-cell seeding + persisted meteor seed (AE2 PR #200) — the template every fix above follows. Included in the pack since; nothing needed in the jar.

How it was verified

  • Launch tests — generate 289 chunks, restart the game, generate again, compare every block and tile entity: byte-identical worlds on the primary test seed; across a 13-seed sample, zero block, ore-type, or chest-content differences.
  • Route tests — same seed generated in three different chunk orders (simulating different walking paths): village buildings/chests and the witchery structure (position and type) came out byte-identical, verified at a live village site on seed 88888888.
  • Community in-game testing caught the witchery type roulette that fixed-route testing couldn't — thanks, and keep reporting.

Known remaining variance fine print

  • Decoration detail — individual grass/flower/tree placement can still differ with your exploration route (a 1.7.10-wide behavior, not practically fixable per-mod). Structures, chests, veins, spawners, dyes, and bees are route-robust.
  • Village piece height — a building can anchor ±1 block of Y depending on approach.
  • Witchery village walls — built on a delayed timer after generation; shape still timing-dependent.
  • Witch counts at witchery structures (entities, not blocks) and internal tile-entity bookkeeping — no gameplay effect on blocks or loot.
  • One rare sky-height anomaly observed once in 26 test runs — still being hunted.
Adopting the jar re-rolls seeds once. The fixes change how randomness is derived, so a seed produces a different — now canonical — world than stock. Old seed notes reset one time, then hold for every runner, every launch. Existing saves are safe: only newly generated chunks are affected.
