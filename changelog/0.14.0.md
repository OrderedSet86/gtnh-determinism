# gtnh-determinism 0.14.0

Since `970e4eafdf3c5103d1b360286ea072f4e13f2eba` (0.13.0).

Three things. **Crash fixes**: 0.13.0 crashes at init on GTNH 2.9.0-RC-1, RC-2 and the current daily
builds (a Mobs-Info 0.6.0 class transformer), and on 2.9.0-beta-1 (GregTech version detection). Both are
fixed, and GregTech ore-vein determinism now covers the GregTech line beta-1 ships. **Mineshaft corridor
chests are pinned**, on by default. **Seed-search and route-map tooling**: stage-0 modules for the hammer%
seed search (3x3 TC hammer rush: smeltery village + 4 Block of Steel + Roguelike TOOLS-chest parts, all
within 20 chunks of spawn), a meteorite prefilter, and the route-map generator, which now ships as a
download with each release.

**This release changes worldgen output; it is not a drop-in for an existing world or corpus.** The
mineshaft corridor chest pin is **on by default** and moves ore-unrelated blocks: measured 137 of 2401
chunks against 0.13.0 on 2.9.0-beta-3 (154 with the pin on, 17 with `-Dgtnhdet.mineshaftpin=false`,
against a 22-of-2401 same-jar launch-to-launch floor), concentrated at y 0–31 where mineshafts live.
The GregTech work below is by contrast output-neutral on 5.09.54.02+ — 17 of 2401 is below that floor,
and disassembly shows every class executing on that band is bytecode-identical apart from constant-pool
index shifts from an added `allow = 2`. So the mineshaft pin is what forces a minor release rather than
a patch.

**The mineshaft pin's before/after delta is now measured.** Route stability itself was already measured
on 2026-09-13 (results/2026-09-13-hammer-prefilter-validation §1: 2.8.4, warm r30, 4 existence
differences of 564 minecart chests, pin ON in both arms) — but that run explicitly carried the caveat
that no stock-pin baseline had been run, so the pin's delta was uncharacterized. That gap is now
closed on beta-3 (results/2026-09-17-mineshaft-multiseed): 25 seeds, r24, rows vs spiral, pin on and
off — existence **19 → 1**, contents and NBT 0 in both arms. Note the two runs use different seed
lists, packs and radii, so 4/564 and 1/318 are not directly comparable; only the 19 → 1 delta is
internal to one experiment.

Both runs land on the same residual class, and a block dump now identifies it: the existence DRAWS are
pinned, the **terrain verdicts are not**. The beta-3 residual is a corridor COMPONENT that exists in
one walk and not the other, so it is a read the mixin deliberately leaves alone, not a failure of the
pin. Absolute residual is 1, not 0 — mineshaft loot is **not** route-independent yet. The remaining
hammer% figures are still design-level and the steel gate must not be trusted in-game until it has its
own measured run.

The reference-seed route map (`-1636594104014467454`, 2.9.0-beta-3, overworld at radius 120) was rebuilt
with this build. Against the previous bundle, 5,137 of 5,142 containers are identical and 1,129 mineshaft
minecart chests are new to the map. The other 7 differences are 2 vanilla-dungeon chests that no longer
generate, a new Witchery dispenser, a new escritoire, and 3 containers with different contents. All 7 are
6–30 blocks from a minecart chest, and each reproduces the previous bundle with
`-Dgtnhdet.mineshaftpin=false`, so they are the pin's block movement described above. On the rebuilt run,
2,394 of 2,394 chests the prefilter predicts are present.

## Fixed

### Crash on 2.9.0-RC-1, and two horse-spawn draws that stopped being seed-stable

`gtnhdeterminism` 0.13.0 crashes at init on GTNH 2.9.0-RC-1, on the client and on a dedicated server:
`Critical injection failure: Redirector gtnhdet$forkedChestZ ... in worldgen.WorldGenDungeonsScanMixin`.
Nothing the jar hooks into changed. The cause is Mobs-Info 0.6.0, new in RC-1, which registers a class
transformer that runs on every class using `java.util.Random`. Wherever `rand.nextInt(n)` is compared
straight away with a constant, the transformer replaces it with a call to its own
`RandomComparison.nextInt(rand, n, constant, op)`. For an ordinary `Random` that returns the same number,
so the pack generates the same world. But the call is no longer a `Random.nextInt` call, so every mixin
that picks a draw by position ("the 4th `nextInt` in this method") counts wrong:

| mixin | on RC-1 with 0.13.0 |
| --- | --- |
| vanilla dungeon chest position | crash: chest Z (ordinal 4) no longer exists, and chest X's selector lands on chest Z |
| mineshaft corridor chests (new in this release) | crash: chest slot A (ordinal 1) no longer exists |
| mesa corridor chests (new, opt-in) | crash when opted in |
| horse spawn type, variant and health | **no error**: 2 of the 7 draws silently stayed on the clock-seeded entity RNG |

The fix keeps Mobs-Info's transformer running; it is how Mobs-Info computes drop odds for NEI. The jar now
finds its draws in both call shapes. A new injection point, `RandomDrawPoint`, counts plain and rewritten
`nextInt` calls as one sequence, so a draw is selected by its stock position on every pack. A draw that is
never a comparison in stock code keeps one injector with `require = 1`. A draw that is a comparison gets a
`@Redirect` for the plain shape and a `@WrapOperation` for the rewritten shape, grouped so that exactly the
stock number of draws must bind, or the game refuses to start. The wrap takes the stock draw through
Mobs-Info's own call, so the random stream advances exactly as it does without this jar. The Eldritch ring
spawner roll is now pinned by position with `require = 1` as well. It was not broken, but it matched "every
`nextInt`", so nothing would have caught a future shift.

Verified by booting four packs and disassembling the woven classes. On 2.7.4, 2.8.4 and 2.9.0-beta-3 every
draw goes to the same plain redirect as before. On RC-1 the rewritten draws go to the wraps and the rest to
the redirects, at the same stock positions. A deliberately wrong group count refuses to start
(`expected 8 invocation(s) but only 7 succeeded`). Measured on RC-1, seed `-1636594104014467454`, r24:
with Mobs-Info's rewrite on vs off, ore veins, all 227 containers (27 of them mineshaft minecarts) and all 9
horses are identical, and the chunk difference (11/2401) is at the launch-noise floor (12/2401). Rows vs
spiral gives the same residuals as beta-3 with the same jar. Repeated on 2.9.0-RC-2 and the 2026-10-11
daily build (GT 5.09.54.221), where a player reported this crash: same result on both. See
results/2026-09-25-2.9.0-RC-1-compatibility, Parts 4 and 5.

### GregTech version detection: crash on 2.9.0-beta-1, and a silent hole either side of it

Reported from a 2.9.0-beta-1 client (GT 5.09.52.594): `gtnhdeterminism` 0.13.0 kills the game at
`FMLInitializationEvent` with `InvalidInjectionException: @Redirect ... gtnhdet$virginStoneType could
not find any targets matching executeWorldgenChunkified(...WorldgenGTOreLayer$VeinPlacement;ZZ)I`.

**Root cause.** GregTech rewrote its ore worldgen **twice**, but `LateMixinLoader.gtOreMixin()` only
knew about two shapes and discriminated on `hasClass("gregtech.api.enums.StoneType")`, documented as
"does not exist before 5.09.54.x". It exists from **5.09.52.31**. The real boundaries:

| Shape | GT band | Reroll probe | `executeWorldgenChunkified` |
|---|---|---|---|
| A | 5.09.50.119 – 5.09.52.30 (2.7.4, 2.8.4) | `Block.isReplaceableOreGen` ×10 | one decl; selection writes |
| B | 5.09.52.31 – 5.09.54.01 (**2.9.0-beta-1**) | `StoneType.findStoneType` ×2 | one decl; accept test FUSED with the write |
| C | 5.09.54.02+ (2.9.0-beta-3) | `StoneType.findStoneType` ×2 | split resolve / test / place |

Every shape-B pack was therefore handed shape C's mixin, whose method descriptor matches nothing there.
Six further F4d injectors were queued to fail right behind it, because the F4d gate keyed on
`hasClass("gregtech.common.ores.OreManager")` and that class also dates from 5.09.52.31 — so fixing
only the first probe would have moved the crash, not removed it.

**Fixes.**

- Shape is now probed **per target, from bytecode**, in the new `GtOreShape`: `resolveVeinPlacement`
  for C, `findStoneType` for B, `isReplaceableOreGen` for A, most specific first. F4d is gated on
  `GTWorldgenerator$WorldGenContainer` naming `resolveVeinPlacement` and `OreManager` naming
  `canSetOreForWorldGenOrAlreadySet` — the classes those mixins actually bind to.
- **Never use a version comparison here.** The rewrite came off a `-pre` branch, so the shapes
  interleave by tag number: `5.09.52.25-pre` is shape B while the higher-numbered `5.09.52.26` and
  `5.09.52.30` are shape A. Ordering is wrong in both directions.
- An unrecognised GregTech now gets **no ore mixin and a loud warning naming the jar**, instead of
  falling through to one that cannot bind.
- New `WorldgenGTOreLayerFindStoneTypeMixin` restores F4 on shape B, using a bare method selector
  (exactly one declaration exists across that whole band) at `require = 2, allow = 2`.
- `WorldgenGTOreLayerMixin` (shape A) went from **`require = 0` to `require = 10`**, the exact probe
  call-site count on all 622 shape-A tags. At 0 it bound nothing silently when misselected — which the
  loader's own javadoc already claimed had been fixed, and had not been.
- `WorldgenGTOreLayerMixin` also **gained the `GtOrePin.appliesTo` gate**. It had none: no dimension
  whitelist and no `gtnhdet.orepin` off switch, so a stock A/B arm was unbuildable on 2.7.4/2.8.4. Same
  defect the 2026-09-07 correction fixed for shape C; it survived here because nothing measured shape A.

### F4d backported to GT 5.09.52.31 – 5.09.54.01

F4 alone does **not** determinise shape B, and shipping it alone would have been misleading.
`generateVein` passes the TRIGGERING chunk as `chunkX/chunkZ`, and three things key off it: the
clipping window `[chunkX+2, chunkX+2+16)`, the probe column `(chunkX+7, chunkZ+9)`, and `localDensity`.
F4 virginises only the *read* in the second — the coordinates still move with the route, so vein
identity stays route-dependent.

Shape C is fixable with four `@ModifyArg`s only because GregTech had already split geometry / accept
test / placement apart and stored a `generationSeed()` to rewind the RNG. Shape B has one fused call
that also writes the ore, so pinning its coordinates directly would relocate ore up to three chunks
away, into chunks Forge never asked for. The split is therefore reconstructed:

- `GTWorldGenContainerDryRunMixin` — one `@Redirect` on the **selection-loop** call
  (`@At(ordinal = 1)`; ordinal 0 is the cached path, which IS the legitimate per-chunk write). It calls
  once pinned to the oreseed inside a `GtOreDryRun` scope, then, if the verdict accepted the vein,
  rewinds the RNG and calls again unpinned to place, and returns the **pinned** verdict so GregTech
  caches the oreseed-pure choice.
- `OreManagerDryRunSuppressMixin` — suppresses the single `World.setBlock` in `setOreForWorldGen`
  during the dry run. Every `rng.nextInt` in `generateLayer` is evaluated *before* that call, so
  suppression cannot shift the stream.
- `OreManagerVirginStoneB1Mixin` / `OreManagerVirginStoneB2Mixin` — virginise the host-stone read the
  test still makes. Two classes because `setOreForWorldGen` was respelled at **5.09.53.11**
  (`findStoneType(Block,int)` → `findStoneType(World,…)`, the `canGenerateInWorld` gate moving inside).
  Separate classes rather than two `require = 0` injectors in one, so whichever is offered must bind.
- The rewind uses `XSTR.getSeed`/`setSeed`, a plain read and a plain assignment with no scrambling, so
  it round-trips exactly. This is the stand-in for C's `placement.generationSeed()`.
- `GtOreFusedWorldgen` invokes the fused overload **reflectively**: the build pins GT 5.09.54.115,
  where that signature is gone from `WorldgenGTOreLayer` and from the `GTWorldgen` superclass, so no
  compile-time type names it. It resolves from the vein instance, never `Class.forName`, which would
  define the class before its mixins apply.

`VirginStoneType` gained `atUngated` for the same 5.09.53.11 split: below it, stock's `findStoneType`
has **no** `canGenerateInWorld` gate, so the existing gated `at()` would have added a dimension filter
stock does not have. That is reachable — `SethClay` claims `hardened_clay` but is restricted to
`DimNames.SETH`, so an Overworld mesa column reads as a hit in stock and a miss under `at()`, and one
flipped sample out of nine flips the reroll and selects a different vein. Invisible to the orepin audit
and to `ASSERT_PROBE`, because it is a divergence from stock rather than a route dependence.

**Support matrix: A = F4 only (no dry run exists and none can be built); B = F4 + backported F4d;
C = F4 + native F4d.** `GtOrePin.logState()` now prints which, so a measurement run's log attributes
itself.

**Measured** (results/2026-09-17-gt-shape-probe-beta1): real 2.9.0-beta-1 pack, seed
`-1636594104014467454`, r24, rows vs spiral, one jar with `gtnhdet.orepin` as the only lever.
Vein-identity residual **35/423 (8.27%) → 0**. The control matches the 7.95% measured for shape C's
Overworld, independent corroboration that this is the same defect and that `orepin=false` is the stock
arm. **Shape C regression re-measured on 2.9.0-beta-3 (GT 5.09.54.133) with the same jar and lever:
38/423 (8.98%) mix + 1 geometry → 0 / 0 / 0, `diff-veincache.py` exit 0.** So the F4d gate rewrite and
`allow = 2` did not disturb the native path, and geometry is confirmed to be a live metric there (the
control registers 1) rather than the hollow 0 it is on shape B. `diff-veincache.py` exits 1 on the
beta-1 full box for `only in one: 2`; both regions decode to oreseed
chunks (-29,-5) and (-35,10), outside the radius-24 walk, and restricting to the walked box leaves
`only_in_one = 0` at every radius while the control's signal survives every restriction — frontier
artifact. Note `geometry differs` is **vacuous** on this band (shape B caches the layer, not a
`CachedOreVein`, so there is no `placement` to compare); do not quote it as a pass. Whole-chunk hashes
remain 67.6% divergent, unchanged in kind from stock's 71.0%, because the pack still carries the other
open defects — that number is not a determinism result and the movement is not progress.

**Behavioural note:** on shape B the `VeinGenerateEvent` now carries the pinned verdict rather than the
triggering chunk's. That is the self-consistent choice — it is the verdict that gets cached — but it is
a visible change for listeners such as VisualProspecting.



## Added

### Mineshaft corridor loot is now visible, predictable and pinned

Three pieces, closing 0.13.0's "minecart chests remain invisible" known limit (was: 156
`EntityMinecartChest` at radius 60, ~930 stacks of `mineshaftCorridor`, ~23% of vanilla-dungeon
loot volume, routemap chest coverage capped near 92%). Corpora produced before this build still
lack them.

- **Probe report** (`WorldgenProbe.buildSearchReport`): walks chunk entity lists for
  `EntityMinecartChest` and emits them into the same per-chunk `chests` array through the same
  `dumpInventory` serializer (position floored). `scripts/diff-chests.py --type=EntityMinecartChest`
  restricts a diff to them; there is deliberately no separate diff-minecarts.py.
- **Prefilter** (`MineshaftPrefilter`, `-Dprobe.prefilter.mineshaft=R` +
  `-Dprobe.prefilter.mineshaftloot=true`): trigger cells by arithmetic replica of the
  `MapGenBase`/`MapGenStructure` protocol (the warm-up `nextInt()` included; golden cross-checked
  once per process against a dispatch pass, dispatch-only fallback when the check fails or the
  generator overrides the formula); real starts dispatched pre-chunkgen under the villageStarts
  reset discipline; loot by replaying the real `StructureStart.generateStructure` per populate
  window against the SeedProbeWorld overlay, windows in ascending (cx, cz) order, Randoms reseeded
  with RWG's populate formula. `SeedProbeWorld.spawnEntityInWorld` now CAPTURES entities during an
  overlay instead of dropping them. Contents and roll count are exact under F10's box-relative
  fork, which already carried the Entity branch; the sim omits `PopulateChunkEvent.Pre` draws, an
  approximation that matters only for what the existence pin does not cover.
- **Fix jar** (`MineshaftCorridorChestMixin`): the two per-section `nextInt(100)` chest-existence
  draws in `Corridor.addComponentParts` are answered from a splitmix fork of (worldSeed, piece box
  anchor, draw index) — keyed per piece anchor in a ThreadLocal, reset at HEAD, stock draws still
  consumed. Bytecode-verified ordinals on the Forge-patched class: direct `Random.nextInt` sites are
  `nextInt(4)` planks (0), chest A (1), chest B (2), spawner `nextInt(3)` (3). NOT pinned:
  `isLiquidInStructureBoundingBox` and the chest-cell air check — measured first, levered only if
  the multiseed diff shows a residual. `-Dgtnhdet.mineshaftpin=false` restores stock.

  **Measured** (results/2026-09-17-mineshaft-multiseed): 25 seeds, r24, rows vs spiral, beta-3, one
  jar with `gtnhdet.mineshaftpin` the only lever. Existence differences **19 (13/25 seeds) → 1
  (1/25)**; contents and NBT 0 in both arms. The residual is seed `-987654321012345678` at
  (-555, 27, -494): a block dump of the containing chunk shows the cell is `minecraft:stone` in the
  rows walk and `minecraft:rail` in spiral, i.e. the corridor COMPONENT is absent in one order, which
  is not the chest draw this pins. That points at `isLiquidInStructureBoundingBox` — but the dumps
  show liquid is identical in both arms, and that check reads the LIVE world at build time, so the
  final state cannot prove it. Candidate, not conclusion. The air check produced no observed
  divergence, which at ~330 chests cannot distinguish "never" from "rarer than 1 in 330".

  The pack's registered generator is Et Futurum's `MapGenMesaMineshaft`, which inherits the vanilla
  trigger formula (only `getStructureStart` is overridden, bytecode-checked on 2.6.2.25-GTNH) — but
  mesa-biome cells build `MesaCorridor` pieces the pin does NOT cover, and the mesa biome test can
  resolve differently worldless vs in-game on a biome border. Mesa mineshafts are unpredicted, not
  mispredicted: rare near spawn on this pack, and F10 still makes their contents position-pure.

### Route-map generator ships with the release

Each release now carries `GTNH-Routemap-windows.zip` and `GTNH-Routemap-unix.zip`. A player unzips one,
runs it, picks their Prism instance and types a seed, and gets the interactive loot/POI/ore-vein map of
their own world in a browser. It turns the instance into a headless server, generates the world with
the fix and probe jars of this release, and builds the bundle with gtnh-seedlib's builder. Java comes
from Prism's bundled runtime. The Windows zip needs nothing installed: it carries python.org's embeddable
CPython 3.12 with the numpy, pillow and certifi wheels. On macOS and Linux it runs the system `python3`,
which needs `pip install numpy pillow`. If the instance already contains a
`gtnhdeterminism` jar, that one is used instead of the bundled jar, so the map matches the world the
player actually plays.

### Hodgepodge FAST_RANDOM changes every MapGenBase reseed stream

Found because the mineshaft trigger replica's golden check tripped on its first run: 8 replica
cells, 0 dispatched starts at them (seed 6638590251101633602) — a complete, self-consistent,
wrong lattice, the exact failure mode the check exists for. Root cause (Hodgepodge sources in
all-gtnh, `SpeedupsConfig.fastRandom` → `fastload.rand.MixinMapGenBase`): the speedup swaps
`MapGenBase.rand` for `StdLCG`, same LCG constants as `java.util.Random` but **`setSeed` stores
the seed raw, without the `^ 0x5DEECE66D` scramble** — so every per-cell reseed in the vanilla
structure-trigger protocol starts from a different state. An offline StdLCG model reproduces the
dispatched lattice exactly (5/5).

The replica now detects the semantics from the live `rand` field's class (StdLCG → raw,
`java.util.Random` → scrambled, anything else → dispatch-only) and the golden check stays as the
end-to-end guard. Blast radius elsewhere: none — villages, strongholds, caves and the Roguelike/
Witchery/oil modules all DISPATCH the real (mixin-transformed) code rather than replicating
`MapGenBase` streams; the mineshaft trigger replica was the first stock-Random replica of a
MapGenBase stream in the repo. Anyone writing the next one: check the rand field first.

### AE2 meteorite prefilter and the biggest-crater hunt

`MeteorPrefilter` (`-Dprobe.prefilter.meteor=C` grid cells around the origin cell): per-cell RNG
replica through the real `Platform.seedFromGrid` (position, start depth, placer seed, size, lava),
`tryMeteorite`'s descent replayed against the placer's real `validSpawn`/`invalidSpawn` sets on
virgin `world.getBlock` — the same reads `Ae2MeteoriteSitingMixin` gives the game — and a
carved-volume score integrating the crater paraboloid over the virgin heightmap. Gates:
`gate.meteorsize` (candidate filter, default 7.8), `gate.meteorrelief` (default 20),
`gate.meteorvol` (seed kill; kill rows carry candidates). `seedsearch/meteor-hunt.py` ranks.
48 ms/seed at C=2 with default gates.

Measured (beta3 = 2.9.0-beta-3, AE2 rv3-beta-1050; identical on 2.8.4/rv3-beta-695): golden seed
existence 6/6, landing 5/5, size exact; multiseed 23-seed warm r30 existence 14/14, landing 10/10,
0 false craters. The crater verdict is the one approximation left: skyMode reads LIVE terrain, so
populate lowering a surface (lakes) produces craters the virgin model calls buried — 3 of 10 in
the multiseed window, all one-way; no false positive has been observed. Hunts: 200k seeds at
size gate 7.8 (top-5 verified 5/5, best 301,197 carved), then 90k at gate 6.5 with a staged
1 -> 3x3 -> 5x5 relief peek (0.5 -> 3 seeds/s) and an `enclosure` ring metric — winner (verified)
403,971 carved at (1284,1935) on seed -1877890734832540703, a size-6.5 roll the first gate would
have dropped: relief dominates size. See results/2026-09-13-meteor-crater-hunt.

Operational note for the next warm batch: `warm-probe.sh` does not create the out-template
directory (every seed fails on FileNotFoundException if it is missing), and a warm 25-seed batch
at the default 6G heap OOMed the server thread after 23 seeds — 16G held for r60; use
`PROBE_XMX`/`-Xmx` deliberately.

## Known limits

- **0.13.0's meteorite work is the OVERWORLD only, and meteorites also generate on Mars.** AE2 gates
  meteorites on an explicit dimension whitelist — uniquely among its worldgen types, since
  `isWorldGenEnabled` ends
  `return !(!isGoodDimension && type == WorldGenType.Meteorites)`. This pack sets
  `meteoriteDimensionWhitelist` to **dim 0 and dim 29 (Mars)**; the Nether and the End are hard
  disabled for every type, and the Twilight Forest is simply not on the list. Mars is absent from
  `minMeteoriteDistance` and `meteoriteSpawnChance`, so it falls back to the `0=` entries and gets the
  same 707 grid and 0.3 roll with Mars debris blocks.

  `Ae2MeteoriteSitingMixin` carries no dimension guard, so it redirects on Mars too. That is
  structurally sound — `TerrainOracle` reads `theChunkProviderServer.currentChunkProvider` and goes
  through `OracleRngGuard.provideChunkIsolated`, so it is not overworld-specific — but it has never
  been run against Galacticraft's chunk provider, and no probe has ever covered dim 29. Every figure
  in 0.13.0 (0 of 44 existence, 0 of 25 crater, +11.4%) is dim 0. **Untested, not verified.**
- **GregTech 5.09.53.11 – 5.09.54.01 has code but no measurement.** `OreManagerVirginStoneB2Mixin` is
  written and gated for that sub-band, but GTNH ships no pack in it, so nothing exercises it. The
  measured band is 5.09.52.31 – 5.09.53.10 (2.9.0-beta-1).
