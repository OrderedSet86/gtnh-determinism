The determinism jar: every fix, and why it was needed

What gtnhdeterminism-0.4.jar changes so that one seed always makes one world. Drop it into mods/ of a stock GTNH 2.7.4 instance — nothing else to install or configure. Companion to the full audit; source and releases at github.com/OrderedSet86/gtnh-determinism.

Nearly every bug is one of four patterns: randomness seeded from the clock instead of the world seed; a conditional branch that consumes random draws only sometimes, shifting everything rolled after it; decisions reading world state that may not exist yet, making the outcome depend on your approach direction; and registries in hash-ordered collections whose iteration order reshuffles every game launch.

Mod / scope Symptom Root cause Fix in the jar
Forge/FMLevery village Same seed, same village spot — different buildings each launch. Smeltery/blacksmith present one session, gone the next; chest loot "cycled between forms." Modded village-building handlers (Witchery, VillageNames, Tinkers, Railcraft, Forestry, WitchingGadgets…) live in a HashMap keyed by class. Classes hash by memory address, so iteration order — which sets both RNG draw order and the building-list order — reshuffles every JVM start. After mod loading, the handler map is replaced with one sorted by class name. One canonical village per seed, for everyone.
Witcherycovens, wicker men, shacks, goblin huts Structures moved between runs; after the first fix they stayed put but the type changed with your walking route — hay man one run, house or circle the next. Spawner contents varied too. Three stacked bugs: worldgen rolled off clock-seeded world.rand; the structure per site was picked by shuffling one shared list in place every chunk, so the winner depended on how many chunks generated en route; the wicker man's spawner mob type was a separate world.rand roll. All rolls use the seeded per-chunk RNG; the site's structure is chosen from a fresh name-sorted copy of the list — a pure function of seed + location; spawner type from the seeded roll.
Thaumcraftnodes, totems, barrows Node types/positions, totems, barrows differed even within one session; barrow urn/crate loot never repeated. All surface features shared one RNG stream with extra draws gated on live terrain reads at chunk borders — one flipped check shifted every later roll. Barrow loot used world.rand; bonus nodes went to whichever chunk generated first; ring mazes were built on a background thread racing worldgen. Each feature gets its own RNG from seed + chunk + feature id; bonus nodes belong to the chunk containing the feature; maze gen is synchronous and seeded; barrow loot rolls from the generation RNG.
Thaumcrafteldritch rings / obelisks A known obelisk was present on one visit and gone on the next — its existence depended on which chunks had generated first (field-reported on seed 88888888). Each candidate ring aborts if any previously generated ring left maze cells within up to a 43×43-chunk window. The maze map fills in population order, so ~25+ candidates per window fought a lottery decided by your route. The altar's spawner-type roll also sat behind live-condition-gated cosmetic draws. One seed-pure site per 25×25-chunk region at stock density: seeded candidates are tested against regenerated virgin terrain with the stock validity rules; ring spacing statically prevents maze overlap, so the race is gone. Spawner and banners roll from seed + position. The maze minigame itself is untouched.
GregTechore vein identity & height Rarely, a known vein came up as a different ore (copper↔iron) depending on approach direction — one flip could cascade into neighboring veins. Vein placement probes a column at the vein's height band; a non-stone hit rerolls to the next vein type, cached region-wide by whichever chunk generated first. The reroll is intended design (high veins skip low ground; mountains matter for tin) — but stock answered the probe from the live world, so other veins' ore, structures, and decoration flipped the answer by route. The same probe, answered from regenerated virgin terrain: the reroll design is preserved exactly, and vein identity/height become pure functions of the seed.
Roguelike Dungeonsposition & carving The region's dungeon relocated ~50 blocks and re-rolled its size (133 vs 156 spawners measured) between two approach routes; deep rooms were damaged differently per route. Placement makes up to 50 attempts, each validated by probing live blocks 40–100 blocks away — terrain that may be raw, decorated, or missing depending on your path. Once placed, every carving decision also read the live world. Placement validates against regenerated virgin terrain, and the dungeon builds through an overlay view — it sees its own writes plus virgin terrain, never route noise. Position, settings, and layout are functions of the seed.
Roguelike Dungeonsfloor decoration One floor's alcove decorations (chest+spawner vs quartz/iron-bars variants) and its mossy/cracked wall pattern reshuffled every game launch — ~1,600 blocks differed between two launches on the test seed, all on that floor. The middle floor of the default stack is built from a minimum-spanning-tree corridor graph whose edges live in a HashSet — and Edge never defines hashCode, so corridor build order (and every wall-variant roll's alignment) followed memory addresses, reshuffled per launch. The edge set keeps a deterministic order (by length, then coordinates). No randomness added or removed — the same floor now builds identically every launch.
Roguelike Dungeonsroom features & chest loot The mess hall's fireplace hopped between walls per launch; storage-room chest alcoves moved; one floor's chests traded item sets between launches while the rest of the dungeon stayed put. Three rooms shuffle their feature/chest placements with Collections.shuffle(list) — the overload that draws from a clock-seeded global. Separately, the loot pass assigned bonus items (specialty gear, enchanted books) by index into the chest list with one shared RNG, so any wobble in chest membership re-dealt a whole floor's picks; one loot method drew everything straight off the shared stream. Shuffles use the room's seeded RNG. Every chest's items come from an RNG forked from seed + chest position; bonus-item picks index a deterministic full chest list, and picks that land on a carved-over chest are simply lost — stock's own loss semantics. Every chest's contents are a pure function of the seed.
LootGamespuzzle micro-dungeons The buried puzzle rooms had a different cracked-brick and broken-lamp pattern every launch (~500 blocks across three rooms on the test seed). Every wall/floor/ceiling "cracked" variant and lamp state is rolled through a static clock-seeded new Random() at generation time. Room placement itself was already seed-pure. Variant rolls draw from an RNG forked from seed + room position — same 10% crack density, pinned pattern. Minigame rewards are rolled when you play, not at worldgen, and are deliberately untouched.
RWGoverworld decoration Trees (large pines, big trees) differed between runs and nudged other features sharing the decoration RNG. Decorations bailed out on terrain checks before consuming their rolls, shifting every later decoration's stream; big trees sized themselves with Math.random(). Every decoration takes exactly one draw from the shared stream and forks a private RNG; the clock-random tree sizing is pinned.
Tinkerssky slime islands Islands in the same places but different size, altitude, and shape every launch. A one-word bug: the generator receives the seeded RNG as parameter rand, but the body used random — an instance field initialized as clock-seeded new Random() (variable shadowing). Use the seeded parameter throughout.
BiomesO'Plentyflora + dirt/gravel patches Flora types swapped and whole underground dirt/gravel patches relocated between launches. Each weighted grass/flower pick rolled with Math.random(), then walked a HashMap in memory-address order. The chosen generator also consumed a different number of draws from the shared decoration RNG — relocating vanilla dirt/gravel patches downstream. Flora tables keep registration order; the pick rolls from the seeded decoration RNG.
ProjectRedlily dye colors Lilies grew in the same spots but their color — the dye they yield — changed every launch. Dyes are run-relevant. The flower color is rolled at tile creation using a clock-seeded default RNG. Color derived from world seed + position: same lily, same dye, always.
Forestryvillage bee house The building was stable, but the bee species inside, apiary frames, and flower garden varied per launch. The building placed from the seeded structure RNG, but its contents rolled off world.rand. Contents roll from a fork of the structure RNG — village bees are a property of the seed.
AE2 fixed 2022meteors — context Meteors (and their chest loot) landed differently per run — the original community finding. Cell-level meteor decisions computed from per-chunk randomness — whichever chunk generated first won — with no persisted per-meteor seed. eigenraven's grid-cell seeding + persisted meteor seed (AE2 PR #200) — the template the fixes above follow. In the pack since; nothing needed in the jar.

How it was verified

  • Launch tests — generate the world, quit the game process, relaunch, generate again, then compare the saved worlds block-by-block and tile-entity-by-tile-entity (a live-world probe can miss late structure writes; region files can't lie): byte-identical on the primary test seed — 1,184 chunks, 372,026 tile entities, zero differences including every chest slot.
  • Route tests — same seed generated in different chunk orders (rows / columns / spiral, simulating different approach paths): structures, layouts, veins, spawners, and all surviving chest contents identical.
  • Balance evidence — a 60-seed stock-vs-fixed corpus shows vein materials, small ores, village pieces, and witchery structure counts statistically equivalent (±10% bounds), plus a 500,000-draw Monte-Carlo over the shipped loot tables certifying rare chest items. Two disclosed, understood deltas: one high-altitude vein type is ~15% more common (stock's live-terrain probe used to reroll it away), and dungeon-placement semantics shift the chest-loot mix slightly.
  • Community in-game testing caught three bugs the fixed-route harness couldn't (the witchery type roulette, the vanishing obelisk, and a stale-jar loot report that exposed a real gap in the loot pass) — thanks, and keep reporting. When you report, include the jar's md5sum with the seed and coordinates.

Known remaining variance fine print

  • Decoration detail — individual grass/flower/tree placement can still differ with your exploration route (1.7.10-wide behavior, not practically fixable per-mod). Structures, chests, veins, spawners, dyes, and bees are route-robust.
  • Deep dungeon chests — whether a bottom-floor chest exists can depend on approach route (a later lava lake can carve the room). Surviving chests' contents never change. A full fix is designed but changes when dungeons appear in-game — pending a community decision.
  • Village piece height — a building can anchor ±1 block of Y depending on approach.
  • Witchery village walls — built on a delayed timer after generation; shape still timing-dependent.
  • Small residuals under investigation — a few dozen deep-underground (y1–4) dirt/gravel blocks toggle per launch, one contested flower position, and a rare sky-height anomaly. None are routing-relevant. Witch counts at witchery structures (entities, not blocks) and internal tile-entity bookkeeping also vary without affecting blocks or loot.
Adopting the jar re-rolls seeds once per jar version. The fixes change how randomness is derived, so a seed produces a different — now canonical — world than stock (and than earlier jar versions: 0.4 worlds differ from 0.3 worlds by design). Old seed notes reset one time, then hold for every runner, every launch. Existing saves are safe: only newly generated chunks are affected.
