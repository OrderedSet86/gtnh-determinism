# gtnh-determinism 0.15.1

Since `90eee857d0cd62c1e596bf0f2a9507a92ce97a16` (0.15.0).

## Summary

- **0.15.0 crashes at startup. 0.15.1 fixes the crash.** The release workflow attached the wrong build
  output to the 0.15.0 release. The source is the same, and worldgen is the same as in a correct 0.15.0 build.
- **The release workflow now stops on a jar like that one.**

## Fixed

### The 0.15.0 jars were an intermediate build output

0.15.0 is the first release built with JvmDowngrader. With JvmDowngrader, the build writes two more jars
beside the release jar: `-downgraded.jar` and `-predowngrade.jar`. Both keep the development (MCP) names and
do not contain the JvmDowngrader stubs. `release.yml` took the first jar in the list that did not end in `-dev`
or `-sources`. That jar was `-downgraded.jar`.

Effect on GTNH 2.9.0, Java 17, `RWG2_CONTINENTS`: the server stopped 17 s after launch with

```
InvalidMixinException: @Shadow field boundingBox was not located in the target class
net.minecraft.world.gen.structure.StructureComponent. Using refmap mixins.gtnhdeterminism.refmap.json
```

In the published jar, `StructureComponentChestMixin` refers to `boundingBox`. In the release jar it refers to
`field_74887_e`. `worldgenprobe-0.15.jar` had the same defect.

`release.yml` now filters out `-dev`, `-sources`, `-downgraded` and `-predowngrade`, and fails unless exactly
one jar is left. A new step fails if `gtnhdeterminism` or `worldgenprobe` has no stubs under its own prefix,
or if a class calls a stub outside that prefix. `scripts/build-jar.sh` uses the same filter.
